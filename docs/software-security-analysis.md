# Software security analysis

Schema 1.15 retains canonical bounded domain scores in `project_identity.domains` and separate categorical labels in `classifications`. `project_inventory` records bounded filename-derived language and dependency-manifest counts, provenance, completeness, and limitations. It does not resolve dependencies or execute builds. Canonical identity uses at most 16 selected manifests, 256 KiB per file and 1 MiB in aggregate. Incomplete observations stay explicit.

Native checks report Python subprocess `shell=True`, imported PyYAML `unsafe_load`, imported `builtins.eval`/`exec`, and explicit Dockerfile `:latest` tags. These AST-aware Python and bounded Dockerfile checks are candidates, without taint or runtime validation.

## Semgrep (experimental)

Use `vigil-fuse scan PROJECT --semgrep-config LOCAL_RULES.yml` to explicitly request host execution of an already installed Semgrep with a local rules file. FUSE rejects configs containing `extends` so Semgrep cannot fetch inherited registry rules, disables metrics and version checks, and does not request registry rules. Host execution is not a network sandbox. To honor strict `--no-network`, FUSE skips this adapter instead of launching it. It also skips the adapter when FUSE path filters or a Docker analyzer sandbox are selected because this adapter cannot yet preserve those boundaries. The report output directory is excluded from the scan.

FUSE validates bounded JSON, paths and locations before normalization. Tool messages and source snippets are not retained. ERROR, WARNING and INFO are mapped to high, medium and low respectively as upstream labels; impact and runtime reachability remain unverified. The lane is reported as partial because file coverage has not been independently verified. Use only trusted local Semgrep rules. No Semgrep version has yet been live-tested for this adapter.

The implementation references the official [Semgrep CLI reference](https://semgrep.dev/docs/cli-reference), [JSON output documentation](https://docs.semgrep.dev/customize-semgrep-ce), and [JSON schema](https://github.com/semgrep/semgrep-interfaces/blob/main/semgrep_output_v1.jsonschema).

## CodeQL (experimental)

Use `vigil-fuse scan PROJECT --codeql-database DATABASE --codeql-queries LOCAL.qls` to request analysis of an existing database with a local query or suite. FUSE never creates the database or runs a project build. The database must be outside the scanned target because CodeQL may write analysis results to it. FUSE requests `--no-download` and disables source snippets and file contents. Host execution is not a network sandbox, so strict `--no-network` skips this adapter. Requested path filters and Docker sandbox mode also cause it to be skipped. The database must correspond to the scanned target; FUSE cannot independently prove that association.

SARIF is size-checked before parsing, with bounded findings and paths. FUSE rejects unverified URI bases and external paths; some otherwise valid SARIF forms may therefore be unsupported. It preserves separate code-flow paths, source/sink labels, selected CWE and precision metadata, but does not prove runtime reachability. File coverage is reported as partial. No CodeQL version has been live-tested with this adapter; its use is subject to [GitHub CodeQL licensing](https://docs.github.com/en/code-security/reference/code-scanning/codeql/codeql-cli/sarif-output). The CLI contract was checked against [database analyze](https://docs.github.com/en/code-security/reference/code-scanning/codeql/codeql-cli-manual/database-analyze).

Use `--sbom` to request an optional Syft CycloneDX inventory, or `--vulnerabilities` to generate the inventory and match its package/version entries against OSV. A supplied CycloneDX or SPDX 2.x JSON SBOM is also reported when either option is selected. `software_security.dependency_inventory` in JSON exposes up to 10,000 bounded component records with name, version, ecosystem, PURL, and inventory source. A component means it appears in the selected SBOM. OSV matches remain advisory observations, and reachability stays `unknown`; neither establishes vulnerable code execution. Recognized PURL ecosystems include npm, Python, Go, Maven, NuGet, Composer, Bundler, Cargo, Dart, Hex, R, and Conan when the selected SBOM contains those entries. FUSE does not automatically install Syft or download package tools. Check the `syft` and `osv-scanner` coverage states before interpreting an empty inventory or advisory result.

## IaC and container configuration (experimental)

`--iac --analyzer-sandbox docker --sandbox-image trivy=IMAGE@sha256:DIGEST` opts into Trivy configuration checks using an already-present local image. FUSE does not pull it. The sandbox has no network access and a read-only target. Terraform module fetching can otherwise cause outbound connections, so host execution is deliberately unavailable. Remote modules and coverage may be incomplete. Trivy output and diagnostics are bounded, and only normalized check metadata is retained. No live Trivy version has been verified for this adapter. See the official [Trivy config CLI](https://trivy.dev/docs/latest/references/configuration/cli/trivy_config/) and [connectivity guidance](https://trivy.dev/docs/latest/guide/advanced/air-gap/).

An actual container image is scanned only when the user supplies `--container-image LOCAL_IMAGE`. FUSE requests the local Docker source only, disables database updates, API calls, telemetry and version checks, and does not request a registry source. The image must already exist in the local Docker engine, and Trivy's vulnerability databases must already be cached; otherwise the analyzer reports failure without downloading either. This host adapter is skipped when Docker analyzer sandbox mode is selected because that sandbox does not receive the Docker daemon socket. It scans vulnerability records only and stores normalized package/advisory observations, not Trivy's full raw report. FUSE preserves the upstream severity label separately from the normalized severity and leaves reachability unknown. The live Trivy executable and Docker image path have not been verified in this environment. See the official [Trivy image CLI](https://trivy.dev/docs/latest/references/configuration/cli/trivy_image/), [local image source behavior](https://trivy.dev/docs/latest/target/container_image/), and [JSON report contract](https://trivy.dev/docs/latest/guide/configuration/reporting/).

## Correlation

FUSE assigns possible correlation groups when software-source observations from different analyzers share one CWE and exact file and line range, when native and historical secret candidates share an exact file and line, or when advisory observations share an advisory identity and package/version. Secret values are not used for correlation. All observations remain in the report; a group is not proof that they describe the same cause. Severity and confidence are unchanged. Configuration findings are not correlated by this rule.

Software summaries expose per-lane statuses and leave unrequested analyzers skipped. Shared secret and workflow observations remain separate from software-specific finding counts. Semgrep and CodeQL record the SHA-256 of the selected local rule or query file, checked before and after execution; referenced files and a CodeQL database are not fully identified by that digest. These observations do not establish a complete configuration or immutable inputs.

`--trivy-secrets --analyzer-sandbox docker --sandbox-image trivy=IMAGE@sha256:DIGEST` opts into a Trivy filesystem secret scan. It requires the locally available digest-pinned image, scans a read-only target with Docker networking disabled, and explicitly disables Trivy's working-directory config, ignore, and secret-config files so target-controlled rules cannot suppress or change findings. The output is parsed with size and path bounds; match text and source snippets are discarded before report persistence. Coverage is partial because Trivy's JSON secret report contains findings only and cannot prove which files were scanned. The lane is incompatible with FUSE path filters. See Trivy's [secret scanning](https://trivy.dev/docs/latest/guide/scanner/secret/), [filesystem CLI](https://trivy.dev/docs/latest/references/configuration/cli/trivy_filesystem/), and [configuration-file security guidance](https://trivy.dev/docs/latest/guide/configuration/).

## Hybrid routing, coverage, and limits

The checked-in `tests/fixtures/software-hybrid` target combines a Python backend, PlatformIO firmware, KiCad design, RTL, and a GitHub Actions workflow. One scan report carries all detected domains, the native software candidate, hardware inventory, RTL analysis, and workflow coverage. A pure software plan marks hardware inventory irrelevant. Existing firmware-specific lanes remain available in the same scan; FUSE does not require choosing a single domain profile.

Coverage is recorded for each lane. An unrequested optional tool is shown as skipped with a `Not requested.` detail. Unavailable, partial, unsupported, failed, and timed-out tools remain visible and do not imply a clean result. Optional analyzers are never installed automatically. Gitleaks only scans Git history when explicitly selected; secret values are redacted before report persistence or local reasoning. GitHub Actions checks are static and limited to documented YAML forms. GitLab CI, general CI taint analysis, active testing, and runtime validation are not implemented.

Report bundles default to a sibling directory outside the target and include JSON, text, SARIF, `CITATION.cff`, and `FUSE_SCAN_PROVENANCE.json`. Explicit output directories are excluded from native discovery and masked inside the Docker sandbox. Provenance includes sanitized analyzer versions, project identity, network mode, configuration digests, and report hashes. No adapter establishes runtime reachability, product deployment, or exploitability.
